Three repos, one platform — kri / pulse / hydra

The thesis: kri is the platform. pulse and hydra are tenants. Today each tenant carries its own platform pieces. Move the platform pieces to kri, leave the workload logic where it lives.
kri — platform plane pulse — CI/CD workload hydra — LLM workload duplicated shared

Today — three islands, each with its own kitchen

Target — kri as the platform; pulse and hydra as tenants

The architectural rule

Touches the Mac? → kri.

Touches the build? → pulse.

Touches the LLM? → hydra.

The four flows that justify the split

① Node onboarding — one path, two tenants

Both tenants register a node profile with kri. kri's UI runs the SSH bootstrap, installs the Salt minion, applies the base role. Today both have separate scripts; replace both with kri's API call.

② Metrics — many publishers, one stack

One OTel gateway, one Prometheus. Each exporter (kri's apple-exporter, hydra's mlx-runtime, pulse's Jenkins metrics) pushes via OTLP. Same pattern that cylon already proves works.

③ Secrets — one store, scoped reads

Tenants ask kri for secrets by scoped name. kri checks RBAC and serves the value. Replaces gitignored hosts.yml, Tailscale auth keys, iOS signing certs scattered across repos.

④ Dashboards — owned by workload, served by kri

Each workload owns the JSON; kri's Grafana sidecar picks up any ConfigMap labelled grafana_dashboard: "1". Hydra already adopted this in PR #19; same pattern for pulse.

Open questions for the platform team
  1. Should kri ship its own Grafana / Prometheus, or wrap an existing kube-prometheus-stack release? Suggest: wrap for now (cylon already proves the pattern), revisit at v1.
  2. What's the contract for "role content packages" handed off to kri? Suggest: OCI artifact via ghcr.io — versioned, signed, immutable.
  3. Do pulse's Jenkins jobs need access to kri's secrets API at build time? Yes for iOS provisioning. Define the auth boundary: Jenkins agent token → kri secret-API scope.
  4. Drift detection coverage — should kri detect drift in apple-silicon-exporter.plist (hydra-owned content)? Suggest: yes; baselines come from hydra, kri scores them.
  5. Namespacing — should hydra's roles be kri-roles/llm-mlx or hydra-llm-mlx once in kri's registry? Suggest: keep workload prefix for origin visibility.
Trade-offs worth naming
  • kri becomes a single point of failure. Mitigated by treating kri itself as workload-on-cluster (HA via standard k8s patterns) and by keeping per-Mac agents capable of running headless when kri is down.
  • kri becomes a release-cadence bottleneck. Counter-pattern: kri exposes stable APIs; tenants pin versions.
  • Workload repos become "less self-contained". Document a standalone dev-mode path (a docker-compose.dev.yml in hydra brings up a minimal local Prom + Grafana).
  • One-cluster assumption. Multi-cluster is a follow-up; kri's API needs cluster scopes.
