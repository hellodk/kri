Deployment

Where to deploy kri

One Docker Compose stack on a laptop, NUC, or rack server — manages macOS and Linux nodes alike via SSH.

Component-wise — deploy/docker-compose.yml

Tenant content mounts

PULSE_REPOS_DIR → /mnt/pulse:ro in Compose — kri discovers pulse playbooks at runtime. Hydra roles migrate to kri's registry over time.

salt-master: Docker vs native

Docker — convenient for development (included in Compose). Native — recommended for production on a dedicated fleet node; point the API via .env.docker.

Related deployments

Blockers

What's blocking us

Real constraints on heterogeneous Apple Silicon hardware and multi-repo integration.

Metal OOM on 16 GB M4

MLX prompt cache ~3.8–4 GB exhausts unified memory. mlx_lm.server aborts with Insufficient Memory. Weight ceiling ~9.6 GB (60% rule).

Air-gap dependency chain

Zero-internet cluster — all Python wheels must flow through on-prem JFrog Artifactory. No public PyPI fallback in production.

Platform code duplication

Parallel bootstrap, monitoring, and secrets in kri/hydra/pulse until platform consolidation completes. Drift risk across repos.

vllm-mlx pre-release

Recommended production path is still rc — needs validation on full 28-node cluster before cutover from mlx_lm.server.

pulse ↔ kri secrets boundary

iOS provisioning profiles need kri secrets API at build time — auth scope (Jenkins agent token → secret-API) undefined.

Single control-plane SPOF

kri becomes release-cadence bottleneck as platform absorbs hydra roles. Needs stable API + version pinning for tenants.
