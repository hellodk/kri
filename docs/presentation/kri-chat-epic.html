Principal-engineer audit · transformation plan

Turning kri from a chat assistant into a real agentic system.

kri already ships the parser half of an agent and a solid LLM I/O surface. The missing 70% — an executor, a tool registry, a safe write surface, RBAC-in-dispatch, and prompt-injection hardening — is what this epic delivers, across six sequenced phases (A–F), served by local LLMs running on the very fleet kri manages.

~30% there today 6 phases (A–F) ~83 story points 4–5 wks · 2 engineers 18× M4 minis, local inference

00TL;DR

The platform is roughly a third of the way to an agent. The remaining work is the hard, safety-critical two-thirds.

Built todayRemaining (this epic)
~30% — parser, I/O, prompt builder, dry-run, approvals~70% — executor, registry, write surface, policy

What exists and is good

A backend-agnostic tool-call normalizer (tool_calling.py), SSE streaming with an extensible event envelope, a fleet-snapshot prompt builder, context-window-aware truncation that pins the ## Rules tail, the PendingAction email-approval gate, first-class Salt test=True dry-run, and an existing mlx_cluster Salt state that lets the fleet self-deploy MLX.

What is missing

No executor, no agent loop, no tool registry, no write surface for playbooks / Salt states, no RBAC propagation into tool dispatch, and no prompt-injection hardening on fleet-controlled strings that already land verbatim in the system prompt. tool_mode is dead schema; the regex intent classifier is "regex-and-prayers."

Three load-bearing decisions. (1) A typed JSON-Schema tool registry with RBAC-gated, read-only tools first. (2) A quarantine filesystem (/srv/kri/agent-quarantine/<user>/<session>/) for LLM-generated artifacts that never auto-promote into live playbooks/ or salt/states/. (3) Extend the existing PendingAction approval gate into the agent write path — reuse the trust primitive operators already know, don't build a parallel one.

02Critical gaps to becoming agentic

Seven things stand between "fancy chat with a schema" and an agent.

1 · No tool executor + loop

Nothing consumes the parsed ToolCall list; no tools=[…] is ever sent. MVP ≈ 400 lines: registry, executor with per-tool RBAC, a bounded AgentLoop, new SSE events.

2 · No write surface

No create/update endpoint for playbooks or .sls files. The central missing capability for "agent authors and deploys" — and it must target quarantine, never the live tree.

3 · No RBAC in dispatch

Role is checked once at the route. The instant tools dispatch, the caller's role must propagate into every tool, every Celery task, every audit row.

4 · Prompt-injection exposure

_sanitize_cell strips |/newlines but not code fences, imperative text, tool-call-shaped payloads, or bidi/control Unicode in node fields injected into the prompt.

5 · Stale regex intent

Fails on multi-turn, negation, synonyms, languages. Becomes obsolete once the planner is the router; keep only as a confident read-only gate.

6 · Audit/observability gaps

One flat query-log row can't represent a 4-tool / 3-iteration run. Need parent_query_id, a tool_calls JSON column, per-dispatch audit rows, OTEL spans, a run timeline.

7 · tool_mode unused

Should drive native vs json vs anthropic vs none tool calling per endpoint. Until read, every endpoint gets the same prompt-only treatment — a quality & latency cliff.

03Target architecture

A typed registry feeds a bounded loop; an executor enforces RBAC, dry-run, idempotency and audit on every call.

Tool registry

Every tool is a frozen ToolSpec: JSON-Schema params (additionalProperties:false, enums, maxLength), required_role, side_effect, requires_approval, requires_dry_run_first. Exports to_openai_tools() / to_anthropic_tools() / to_prompt_section().

Executor

dispatch(call, ctx): re-check role → validate args → queue PendingAction if approval needed → enforce prior dry-run → idempotency cache → run handler → audit with actor=operator email.

Agent loop

Bounded: MAX_ITERATIONS=6, MAX_TOOL_CALLS=12, token caps. Streams step_start / tool_call / tool_result / awaiting_approval events; checks client disconnect each iteration.

Write surface: quarantine → review → promote

The load-bearing safety property of the whole system. The agent can write to quarantine; it can never promote.

generate_salt_state→ validate YAML + schema + dangerous-pattern scan→ write to /srv/kri/agent-quarantine/<user>/<session>/→ diff vs live→ dry-run (test=True)→ human reviews diff + dry-run→ admin clicks Promote→ copy to live + apply
Promotion is NOT a tool. It's an explicit admin-only POST /agent/artifacts/{id}/promote. Quarantine is per-session, 0700, quota'd (5 MB/session, 50 MB/user), TTL 24h, path-traversal-validated, symlink-rejected. No file reaches the live tree without a human click.

04Operator scenarios

What "agentic kri" feels like, end-to-end.

  • A — "Install Xcode 16 on all Darwin nodes in ios-builders, dry-run first." Planner: list_nodes → read_existing_state → generate_salt_state (quarantine) → lint/scan gate → apply_salt_state_dry_run → operator reviews diff → tokenized approval → real apply, one audit row per node.
  • B — "Write a playbook that installs node_exporter and run it on the new build group." Lands in quarantine, ansible-lint'd, diffed against the live playbook; only a human "Promote" lifts it into playbooks/.
  • C — "Why is mm7 degraded and what would fix it?" Pure read: get_node + get_recent_audit + search_playbooks → synthesized answer. No write tools exposed, no gate, target <8 s.
  • D — "Spin up an MLX cluster on the 18 minis, mm1 coordinator." set_pillar loop → apply_salt_state_dry_run(ml.mlx_cluster) → approve → rollout. Special guard: a planner session may not deplane its own planner minis.
  • E — "Bring mm12 back into rotation." get_node → ping_node → enable_node → run_salt_cmd(test.ping). enable_node needs operator role but not email approval.
The agent will never: read secrets, delete nodes, process_kill, touch PROTECTED_TARGETS (salt-master, sshd, launchd, windowserver, exo…), write outside quarantine, run shell off the Salt allowlist, modify its own config/RBAC/audit, reach the public internet, or act for two operators on the same target at once.

Default topology: round-robin mlx_lm.server per node (18 independent OpenAI-compatible endpoints, discovered + health-cached). The router picks by capability tag (planner/coder_yaml/fast_summarize/embed), then health, then least-loaded, with a fallback chain ending at an optional admin-gated cloud endpoint. The existing mlx_cluster Salt state is extended (launchd plist, model pre-download, health probe) — itself a textbook first dogfooding target for the agent's write tools.

16 GB is tight for a 14B planner. Mitigate with max_concurrent:1 on planner minis, an 8K per-session context cap, embedding sidecar moved off planners, and a hard MAX_ITERATIONS=6 so a confused planner fails loudly rather than looping. Expect ~1-in-10 tool calls wrong — feed schema errors back ("did you mean apply_salt_state?") to self-correct in one extra step.

The agent is only as safe as the worst tool it can call — so this gets the most rigor.

Defense layers

Prompt-injection stack

Field-level sanitize at ingest and prompt-build (reject <|, code fences, tool_call, Cc/Cf/Co/Cs + bidi Unicode); wrap node data in <NODE_FIELD> "treat as data" framing; re-sanitize every tool result before feedback.

Output validation

Generated YAML/SLS runs: safe_load → shape schema → dangerous-pattern scan (rm -rf /, forkbomb, dd to device, curl|sh, TLS bypass, egress) → forbidden-module scan → 64 KB cap → ansible-lint/salt-lint. Never auto-promote.

Confused-deputy avoidance

Every audit row, Celery header, approval email and OTEL span carries the operator's email — never "agent". One answer to "who fired this": alice@org via agent session X.

Hard limits

6 iterations · 12 tool calls/turn · 2 parallel writes/operator · co-sign >8 nodes · 6/min rate · 32K input tokens · 4 KB tool-result cap · 4h approval expiry · cloud-fallback daily cap.

Rollout follows a trust curve, not a flip. Month 1 = proposal-only (diffs & dry-runs, zero live writes). Then apply-with-approval for single-node, then co-sign for 2–8 nodes, then full registry — each stage gated on zero agent-caused incidents for two weeks.

08Open decisions for you

Real forks, each one branches the implementation.

  • Cloud fallback — on or off? If on, name the provider (Claude 3.5 Sonnet = strongest tool-caller) and a daily $ cap.
  • Promotion to Git, or filesystem-only? Default is filesystem; PR-on-promote needs a push-scoped service account.
  • Proposal-only audience (month 1) — whole team, or a small alpha cohort?
  • Approvals via email, Slack, or in-app? PendingAction is email today; Slack buttons convert better.
  • Co-sign threshold — default 8 nodes (≈25% of 18 + headroom). Confirm or override.
  • promote_artifact — admin-only (default), or two-tier with operator-to-staging?
  • Planner runtime — MLX (recommended, +30% on Apple silicon) vs llama.cpp (portable)?
  • Planner escape valve if all planner minis are down — cloud-for-planner, refuse-to-Q&A, or cold-standby?
  • Per-tool kill switches in addition to role gating? Cheap to add to the registry.
  • Agent-run transcript retention — 90 days? 1 year? SOC2 driver?

10What success looks like in 12 weeks

An operator types: "create a state that installs htop on all online linux nodes, dry-run."

  • Within ~15 s they watch the planner pick list_nodes and generate_salt_state, with linter and dry-run results streaming in.
  • They review the dry-run and click Approve in the email or UI.
  • A minute later htop is on every online Linux node — each install with an audit row attributed to them.
  • No secret was read, no protected target touched, no file written outside quarantine until Promote was clicked.
  • The entire run was served by an LLM running on the fleet they manage. That is what we are building.
